Speaker note: 30 phút đầu GV trình bày mục 1 đến 4 và đề bài. 65 phút tiếp theo nhóm thực hành, 25 phút cuối trình bày.

Speaker note: Tài liệu viết tay trong README hoặc Google Docs lỗi thời ngay khi code đổi mà không ai biết. OpenAPI có ích khi nó được dùng để kiểm tra, không chỉ để hiển thị. Cùng một file còn sinh được typed client ở frontend; tuần này chưa yêu cầu phần đó.

Speaker note: Trích đoạn chưa đủ các response 404, 409 và 422 của đề bài; nhóm phải bổ sung. Schema, parameter và response dùng lại qua $ref trong components. operationId đặt tên ổn định cho thao tác, dùng khi sinh client hoặc đọc log.

Speaker note: additionalProperties false làm body có field lạ bị từ chối. format uuid chỉ được kiểm tra nếu validator bật kiểm tra format, nên nhóm phải gửi thử product_id sai định dạng. Một số validator mặc định ép "2" thành 2; nhóm phải kiểm tra cấu hình thay vì giả định.

Speaker note: Nhóm được chọn một trong hai cách. Yêu cầu chung là tài liệu và validation dùng cùng một nguồn schema; nếu viết schema hai lần (một trong YAML, một trong code) thì hai bản sẽ lệch nhau. Tên thư viện là gợi ý, nhóm có thể dùng thư viện khác và giải thích lựa chọn.

Speaker note: Boundary là điểm request đi vào API. Validation schema chạy trước handler nên request sai không chạm DB. Rule cần đọc DB (tồn kho, trạng thái cart) không viết được bằng schema và nằm trong service. Hai loại lỗi trả status khác nhau, xem slide sau.

Speaker note: Trong OpenAPI 3.1, nullable viết bằng type gồm kiểu dữ liệu và null theo JSON Schema; từ khóa nullable của 3.0 không còn dùng. Với PATCH, key vắng mặt nghĩa là không đổi, còn null có thể nghĩa là xóa giá trị; nhóm phải ghi rõ trong spec.

Speaker note: 404 dành cho resource nằm trên URL. product_id nằm trong body nên không dùng 404: client sẽ hiểu nhầm là cart không tồn tại. 500 dành cho lỗi phía server như mất kết nối DB. Client dựa vào status để quyết định sửa input (4xx) hay thử lại sau (5xx).

Speaker note: Mọi lỗi, kể cả lỗi validation do thư viện sinh ra, phải đi qua một error handler chung để có cùng dạng. Thư viện validation thường có format lỗi riêng; nhóm cần chuyển về dạng này. details chỉ bắt buộc với VALIDATION_ERROR.

Speaker note: Logging trong tuần này là gợi ý, không chấm chi tiết định dạng. Khi demo, nhóm nên cho thấy từ request_id trong một response lỗi tìm được dòng log tương ứng. Structured log, metrics và tracing được dạy đầy đủ ở Block 15.

Speaker note: GV không cung cấp starter. Nhóm dùng coding agent để dựng project, nhưng phải chạy được migration và seed từ lệnh ghi trong README. Không có frontend trong bài này; nhóm kiểm tra bằng /docs, file .http, curl hoặc test tự động. Cart API được dùng lại ở các tuần sau (checkout, WebMCP).

Speaker note: Nhóm viết migration theo đúng tên bảng, cột và constraint trên slide để GV chấm được bằng cùng ma trận. Công cụ migration (node-pg-migrate, Knex, Prisma, Drizzle) do nhóm chọn. Giá lưu bằng integer cent để tránh sai số số thực.

Speaker note: Constraint trong DB là lớp bảo vệ cuối. API không được dựa vào lỗi DB để trả 400, vì lỗi constraint mặc định thành 500.

Speaker note: Response cart gồm id, status, items (product_id, name, unit_price_cents, quantity, line_total_cents) và subtotal_cents. Server tính tiền từ price_cents trong DB. Nhóm tự đặt schema chi tiết trong spec.

Speaker note: Client không gửi giá. POST và PATCH trả toàn bộ cart để client cập nhật subtotal mà không cần gọi GET thêm. DELETE item không tồn tại trả 404 ITEM_NOT_FOUND.

Speaker note: Thêm vào giỏ không trừ stock; stock chỉ kiểm tra tại thời điểm thêm hoặc sửa. Giữ chỗ tồn kho và race condition khi nhiều người cùng mua là nội dung Block 6. Nếu product đã có trong cart, client dùng PATCH để đổi số lượng.

Speaker note: GV clone repo, làm theo README trên máy sạch và chạy script evidence; không chạy được từ README thì chưa đạt. Script có thể là file .http, bash dùng curl hoặc test tự động (supertest, vitest). Logging chỉ là gợi ý, không chấm định dạng.

Speaker note: DB không đổi phải được chứng minh bằng query hoặc GET sau request lỗi, không suy ra từ status. Nhóm ghi rõ kịch bản nào chưa kiểm tra.

Speaker note: Dòng cuối có thể dùng response validation của thư viện hoặc test so response với schema. Nếu một response lệch spec, nhóm sửa code hoặc spec và chạy lại dòng đó.

Speaker note: Mỗi lỗi trên đều cho happy path chạy đúng, nên chỉ lộ ra khi chạy ma trận. Agent thường sinh ra lỗi thứ hai và thứ tư nếu prompt không nêu error contract.
